-- DECISIONS FOR USER --
  Q: Should the typed hook option use per-hook (one file per hook) or envelope (all hooks in one JSON array) structure?
     - Per-hook: One .json or .sh file per hook name; mirrors legacy per-file pattern; clear event intent; easier to override p
     - Envelope: Single hooks.json (or kiro-memory.json) with hooks:[...] array; matches live auto-memory pattern; proven to wo
     => REC: Envelope. autoMemory.nix proves it works in production; reduces file proliferation; simplifies HM↔devenv sync (one file to install vs. many).
  Q: Should typed schema be defined inline in Nix or external in JSON/YAML?
     - Inline Nix submodules: Load-bearing definition lives in the factory; full module-system validation; tightest control; ha
     - External JSON Schema: Single source for validation tools; easier to document; harder to keep in sync with Nix option ren
     => REC: Inline Nix submodules (primary), with optional JSON export for docs/CI. The module system is the source of truth; JSON schema is derived.
  Q: Should matchers use glob patterns, regex, or both?
     - Glob only (like Kiro permissions): Simple, matches existing precedent, covers ~95% of use cases
     - Regex: Powerful, flexible, but higher learning curve; risk of performance bugs
     - Both: Glob by default, regex as escape hatch (type: enum ["glob"|"regex"] + pattern string)
     => REC: Glob only for Phase 1. If power users need regex, add as Phase 2+ follow-up (or accept raw command flags like --matcher-regex).
  Q: Should legacy untyped hooks (attrsOf lines) coexist with typed hooks, or migrate immediately to typed-only?
     - Union type (oneOf [legacyType typedType]): Backward compatible; allows gradual migration; complex validation
     - Typed-only: Clean break; forces migration; may break existing consumer configs
     - Parallel options (ai.claude.hooks + ai.claude.hooksTyped): Clear intent; no collision; verbose
     => REC: Union type on same option name (ai.claude.hooks). Allows attrsOf lines OR typed submodule; deprecation notice on legacy arm; gives consumers time to migrate.
  Q: Should prompt-based hooks be included in Phase 1 typed schema?
     - Include: Complete coverage of all hook types; consumers can opt-in to use prompts; requires model invocation + token cos
     - Defer to Phase 2+: Focus Phase 1 on shell + HTTP + agent types; prompt is orthogonal complexity; auto-memory doesn't nee
     => REC: Defer to Phase 2+. Phase 1 covers shell/HTTP/agent handlers only. Prompt-based hooks require separate cost tracking and LLM integration; out of scope for initial schema.
  Q: Should Kiro v2 (embedded hooks) be supported with full typed schema, or marked as transitional (v3-only going forward)?
     - Full v2+v3 support: Compatibility layer; v2 users get typed options; added complexity (two schemas to maintain)
     - v3-only: Cleaner; v2 users get auto-migration prompt; aligns with Kiro's v3 push
     => REC: v3-only in Phase 1. Mark v2 as transitional; recommend migration. If production v2 users exist, add compat layer as Phase 2+ follow-up.
  Q: Should hook verification tests be manual CLI gates or hermetic unit tests?
     - Hermetic only (static checks + stub inputs): Fast, sandbox-safe, no token burn, sufficient for schema validation
     - Manual CLI gates: Catches integration bugs, expensive (tokens for Claude), required for production but not Phase 1
     - Hybrid: Hermetic in nix flake check; manual gates in CI (expensive, gated feature)
     => REC: Hermetic in Phase 1-3 (nix flake check, stub-based integration tests). Manual CLI verification deferred to Phase 5 or as optional pre-release gate.
